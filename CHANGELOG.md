## [Unreleased]
### Security
- **Weak Ed25519 keys in the trusted set are refused** (spec, Go and TypeScript SDKs): a non-canonical encoding or one of the eight small-order points is `invalid_key_set` when used, before the signature check. With the identity as public key, Go's crypto/ed25519 accepted a chosen signature (R = identity, S = 0) for any payload, so a tampered key set could make a forged license verify in Go builds while OpenSSL-based SDKs refused it. LicenseForge never generates such keys; the rule guards the embedded key set and makes every SDK answer the same. Six new `lf1.json` vectors, including that forgery.
- **Database connections must verify the server** (ADR-0024, SC-8): the server, `licenseforge migrate`, `audit prune` and the `tenant` commands refuse to start with a database URL that doesn't verify the server's certificate (`sslmode=disable`, `allow`, `prefer` (the driver's default), `require`, or `verify-ca` without `sslrootcert`) unless every host is `localhost`, a loopback address or a Unix socket. Use `sslmode=verify-full` (or `verify-ca` with `sslrootcert`). Every database TLS connection is TLS 1.2+. `LICENSEFORGE_DATABASE_ALLOW_PLAINTEXT=true` (Helm `databaseAllowPlaintext`, rendered on the server, migration and retention) lifts the check for development clusters (any other value is an error; the server warns at every start); the e2e environment sets it. **Upgrade note:** a deployment whose URLs don't verify the server (to a non-local host) won't start until they do; the Helm migration Job fails first, while the old pods keep serving.
- Client TLS policy is tested in both builds: TLS 1.1 servers are refused, and in FIPS 140-3 mode a server offering only non-approved suites (ChaCha20) is refused.

### Changed
- Decided (ADR-0024, ADR-0021, ADR-0010): no ECDSA P-256 key type. Bouncy Castle FIPS Java 2.1.1 approves Ed25519 (FIPS 186-5, FIPS 140-3 certificate #4943), so the Java SDK (v0.2) will verify license files in FIPS mode with the existing Ed25519 keys; Ed25519 stays the only key type.
- ADR-0044 (outbound webhooks) accepted: events derived from the tenant's audit chain (the outbox), Standard Webhooks signatures, ordered at-least-once delivery per endpoint with retries over about 28 hours, then the endpoint is disabled; https only, no redirects, destination addresses checked at dial time. Not implemented yet.
- ADR-0021 amended (and ADR-0024's release line): SDK releases use their ecosystem's integrity mechanism; the Go SDK, a Go module, relies on the Go checksum database, not cosign, which makes versions tamper-evident but doesn't authenticate the publisher. Its first release is postponed past 0.1.0-alpha.1. PS.2 and SR-11 say so, with the `sdk/go/v*` tag protection gap.
- Compliance documents reflect the release pipeline that shipped with 0.1.0-alpha.1: CM-8 (SBOMs) and SR-4 (provenance) are implemented; SI-7, SR-11 and SSDF PS.2/PS.3 record the signatures with their remaining gaps (the Go SDK isn't published; releases aren't immutable); SC-13, SI-2, RV.2 and the Secure Configuration Guide point at the published, signed `-fips` images and signed releases instead of "planned".

### Added
- TypeScript SDK offline formats (ADR-0043): `encodeRequest`/`parseRequest` (`lfreq1`), `encodeReceipt`/`parseReceipt` (`lfrcpt1`), `fileSHA256` and `offlineSHA256`, with the Go SDK's rules (no unknown fields, a bound fingerprint, `kubernetes` exactly for a cluster binding, a 16-byte nonce, the request size limit). The encoders sort keys as Go does and check their own output. Passes `offline.json`, including its `file_hashes`.
- TypeScript SDK fingerprints (ADR-0017): `hash`, `compute` and `forLicense`, with the same sources, order and rules as the Go SDK.
  - Sources: the vendor override, the `LICENSEFORGE_FINGERPRINT` environment variable only when allowed, Kubernetes (the `kube-system` namespace UID, with transient errors retried and RBAC or certificate errors failing at once), and the OS machine ID.
  - Linux `/etc/machine-id` is refused on tmpfs/ramfs and in application containers unless the host's file is bind-mounted; system containers keep their own.
  - Windows and macOS use `MachineGuid` and `IOPlatformUUID`.
  - Passes `fingerprint.json`.
- Fingerprint spec and Go SDK: `/proc/self/mountinfo` fields are split on single spaces only (the kernel escapes space, tab, newline and backslash). Go's `strings.Fields` also split on `\v` and Unicode spaces, so a path containing one read differently than in the TS SDK.
- TypeScript SDK: `parseKeySet` reads the trusted key set's JSON (the dashboard's, the vectors' `keys`) under the same rules as Go's `ParseKeySet`: a non-empty array of objects with exactly `kid`, `alg` and `public_key`, exact-case and unrepeated, string values, the kid pattern, canonical base64url; valid UTF-8 or well-formed strings without a BOM. Anything else is `invalid_key_set`, with messages that don't echo the file. The vector tests load their keys with it.
- TypeScript SDK, first part (`sdk/ts`, ADR-0010; not published yet): `verify`, `parseClaims`, `check` and `open` for `lf1` license files, with `Entitlements` (`hasFeature`, `limit`, `allows`). It has a strict JSON reader of its own, since `JSON.parse` accepts duplicate keys, folds number forms and keeps lone surrogates. It passes all of `lf1.json` and `lf1-claims.json`. Node 22+ (ADR-0010 amended from 20, now end of life), no runtime dependencies; CI runs it on Node 22 and 24.
- Dashboard test mode (ADR-0047): a test-mode tenant shows a "Test mode" banner on every page and "(test)" in the tenant switcher; its signing keys page says to trust its keys in development and CI builds only. Platform admins tick "Test mode" when creating a tenant, and the tenant list marks test tenants.
- `licenseforge api METHOD PATH [--data JSON|@FILE|-] [--idempotency-key KEY]` (ADR-0048): one REST API request with `LICENSEFORGE_URL`, `LICENSEFORGE_TOKEN` and `{tenant}` from `LICENSEFORGE_TENANT`, printing the JSON answer. Exit 0 ok, 1 the API refused (problem on stdout, summary on stderr), 2 usage (nothing sent), 3 unreachable. Paths stay under `/api/v1` on that host (no other host, `..` or encoded dot segments, no redirects followed); https only except loopback; a base URL with a stray `?` or dot segments, or a token with whitespace, is refused (also for `offline`); an answer over 16 MiB fails rather than print cut. `docs/cli.md` has recipes. It is the admin CLI: there is no separate `lf` binary.
- Test-mode tenants (ADR-0047): `POST /platform/tenants` takes `"test": true` (default live; null is 422) and `licenseforge tenant create --test`; `test` appears in the platform tenant list and in `/me/tenants`, and `tenant.create` records it. Set at creation and never changed: the serving login has no UPDATE grant on the column, and a restrictive policy holds the platform pool. A test tenant has its own keys, so release builds that trust a live tenant's keys never accept its files. Platform-level usage measures (hosted billing) are to leave test tenants out; a test tenant's own summary and charts still show its data.
- Dashboard overview charts (ADR-0046): the last 30 UTC days of licenses issued, machines activated and machines deactivated, as one column chart each, with the total in its title, each day's count as its tooltip, and the same numbers as a table.
- Daily metrics (ADR-0046): `GET /tenants/{t}/metrics/daily?days=N` (1–90, default 30) answers, for each UTC day ending today (by the database clock), oldest first and every day present, the licenses issued, machines activated (online or offline) and machines deactivated, in the caller's product scope (license:read). Counted from the license and activation rows; two new indexes on `activations` (built concurrently) bound the scan to the window.
- Go SDK: `licensefile.ParseKeySet` loads a trusted key set from the license format's JSON (the dashboard's, the vectors' `keys`): an unknown or empty alg, a duplicate kid or a wrong key length load as given and surface in `Verify`; malformed JSON or UTF-8, other, missing, repeated or case-variant fields (`encoding/json` alone would fold case and keep the last duplicate, so one file could read as different keys elsewhere), a bad kid, non-canonical base64url (line breaks included) or an empty set are `ErrInvalidKeySet`. The conformance test loads the vectors' keys with it. The spec states the JSON form.
- Dashboard: Settings → Signing keys (ADR-0026). Members whose access covers every product see the keys (status, created, activated, retired or discarded) and the **trusted key set** to embed in builds (pending, active and retired-after-signing keys; discarded ones left out) as Go source for the SDK (`licensefile.KeySet` with the key bytes) and as the license format's JSON, each with a copy button (off when not every key is listed), and a warning to remove a compromised key. A tenant with keys but none active is told nothing can be signed until a pending key is promoted. Owners generate a key (the first is active at once; later ones pending, and only while none is pending), promote a pending key after a warning that names the key it retires, says it can't be undone, and to promote only once every deployed build trusts it, or discard it (with what to do if it leaked).
- Dashboard maintenance (ADR-0045): a plan's edit form sets "Maintenance (months)" (empty: every build); a license's details show "Updates until" and, with license:write on a license that isn't revoked, renew it through the end of a picked day (UTC) or cover every build.
- Maintenance end per license (ADR-0045): an issue request may set `updates_until` (a contract's date) instead of the plan's `updates_months` (not null: 422); `POST /tenants/{t}/licenses/{id}/updates-until` with `{"updates_until": <date-time> | null}` renews, corrects or clears it (license:write; whole seconds, after the issue, year 9999 at most in UTC; the key is required, null covers every build; 409 on a revoked license). Audited as `license.updates_until` with the previous value. Online leases carry it from their next refresh; offline files already issued keep theirs.
- Maintenance term on plans (ADR-0045): `updates_months` (1–1200, or null for every build). A license issued on the plan gets `updates_until` = issue + that many calendar months, whatever the expiry basis, in whole seconds; its leases and offline files carry it, and the SDK refuses builds dated later (`updates_expired`, with `BuildDate`). Plans' `updates_months` and licenses' `updates_until` are in the API; a database CHECK keeps `updates_until` after issue. The issue answer now also shows `max_rehosts` and `rehost_count` (it showed unlimited); an idempotent replay of an issue answered before the upgrade returns the stored body, without these. The `license.issue` audit entry records `updates_until`.
- Docs: [Webhooks](docs/webhooks.md): the event catalog, what a receiver gets, verifying signatures (Standard Webhooks libraries, or a standard-library Go function that the test suite runs verbatim), delivery and retries, recovering stuck deliveries, operator settings. Compliance: AU-2 lists the webhook actions, SC-8 webhook transport, SC-12 signing-secret handling, SC-13 webhook signatures (matrix and OSCAL).
- Dashboard: Settings → Webhooks (ADR-0044). Members who see the whole tenant see each endpoint's masked URL, events, status and delivery state (up to date, sending, retrying with the next try, an event held back) and its delivery log; owners and admins add endpoints (the signing secret is shown once), edit URL and events, disable and enable, skip the held event or skip to now, rotate the secret (after a confirmation explaining the 24-hour overlap; shown once) and delete. A disabled endpoint with nothing known pending reads "Paused"; product-scoped members are told webhooks are tenant-wide; every row action names its endpoint for screen readers. Secrets stay in component state, never in the query or mutation cache.
- Webhooks API (ADR-0044): `GET/POST /tenants/{t}/webhooks`, `GET/PATCH/DELETE /tenants/{t}/webhooks/{id}` (PATCH is a merge patch; `url` and `events` can't be null), `POST …/{id}/rotate-secret`, `…/disable`, `…/enable`, `…/skip-event` (`{seq}`), `…/skip-to-now`, and `GET …/{id}/deliveries` (the 7-day delivery log, newest first, with fixed error texts: timeout, connection failed, tls, redirect, http and the status). An endpoint's `delivery` shows its position, retries, next attempt, whether a send is in flight, and `next_seq` (the event held back, what skip-event takes). Reads need webhook:read, changes webhook:write, tenant-wide; URLs show only scheme, host and port; the signing secret only on create and rotate. Refusals: 422 with the field, 409 `webhook_limit_reached` (10 per tenant) and `invalid_state`. The receiver payload schemas (`WebhookPayload`, `WebhookLicenseData`, `WebhookActivationData`) are in the OpenAPI spec.
- Webhook delivery runs in every server pod (ADR-0044): `LICENSEFORGE_WEBHOOK_WORKERS` (default 8, 0 for none), `LICENSEFORGE_WEBHOOK_ALLOW_CIDRS`, `_DENY_CIDRS` and `_PORTS` (invalid values stop the server). Delivery records older than 7 days are pruned hourly. Metrics without tenant labels: `licenseforge_webhook_deliveries_total{outcome}`, `licenseforge_webhook_dispatch_errors_total`, `licenseforge_webhook_endpoints_disabled`, `licenseforge_webhook_lag_seconds`. Helm: `webhooks.*` values and a NetworkPolicy egress rule to receivers on the allowed ports (none with no workers). **Upgrade note:** the server pods' egress widens to any destination on 443 (narrow `webhooks.egress.to`, or set `webhooks.workers: 0`); the server refuses internal and metadata addresses itself. The dispatcher starts when the server is about to serve and is stopped before the database closes. Endpoints can't be created yet (API next). `licenseforge_webhook_lag_events` too; the disabled gauge counts the dispatcher's disables only.
- Webhook dispatcher (ADR-0044; not started by the server yet): `webhooks.Dispatcher.Once` claims one due endpoint at random (at most 2 leases per tenant across the cluster, checked under a per-tenant lock), moves its cursor past entries that aren't its events (and past a retention cut, audited), sends the next event signed with the current and, during a rotation, previous secret, and records the attempt only if its claim still holds (seq, attempts and lease pinned: a skip, re-enable or delete meanwhile makes it miss). Failures retry on Svix's schedule with jitter (never sooner than Retry-After); the last failure, a 410, or a URL or secret that is invalid for the keyring disables the endpoint (audited; never over a user's disable or a URL or secret changed during the send); a key this replica doesn't have yet, or a cancelled send, releases the claim (backing off 5 minutes for the key) without counting an attempt. A slow receiver's result is still recorded (the write's deadline starts after the send), and an event committing during a claim is never passed over. Payloads follow each event's schema, built from the audit entry alone.
- Audit entries of license transitions (suspend, reinstate, revoke) and of activations (online and offline activation, deactivation by the SDK or the dashboard, offline return) now record the customer, product, plan (ID and slug) and expiry, or binding and seat mode, as at the change (a transition reads the license under its lock): what webhook payloads are built from (ADR-0044), without reading current rows later.
- Webhook egress guard and signer (ADR-0044; not wired yet): `webhooks.Guard` checks every address a delivery dials (after DNS, each candidate): the IANA IPv4 special-purpose ranges and every IPv6 address outside global unicast (plus its not-globally-reachable parts) are refused unless `LICENSEFORGE_WEBHOOK_ALLOW_CIDRS` allows them; the well-known NAT64 prefix is checked as the IPv4 it carries, the local-use NAT64 block, 6to4, Teredo and IPv4-compatible forms are refused; this host, link-local and cloud metadata and service addresses (AWS `fd00:ec2::/32`, Google Cloud `fd20:ce::/32`, Alibaba, Oracle, Azure's 168.63.129.16) are refused even when allowlisted; `LICENSEFORGE_WEBHOOK_DENY_CIDRS` adds ranges, matched against the address as dialled and as decoded (a NAT64 or IPv4-mapped deny holds); ports 443 unless `LICENSEFORGE_WEBHOOK_PORTS` says otherwise. The delivery client uses no environment proxy, the pure-Go resolver, TLS 1.2+ and never follows redirects. `webhooks.Signature` and `Send` implement Standard Webhooks v1 (checked against its reference vector) and classify each attempt as http (status), timeout, connection (no duration: a blocked destination fails at once), tls or redirect, with Retry-After honoured up to 10 hours; a cancelled send is an error, not an attempt; only https URLs are sent.
- Webhook recovery actions (ADR-0044; no API yet): disable (stops deliveries, keeps the position), enable (a disabled endpoint resumes at the event it stopped on, with a fresh retry schedule), skip this event (only the endpoint's next subscribed event: refused if it was delivered meanwhile or isn't that event) and skip to now. Each runs under the endpoint's locks; enable and the skips reset the retry state; each is audited with what it did (a skip records the position it skipped from). `webhooks.EventType` maps audit entries to events (an offline activation only for a new seat).
- Webhook endpoint service (ADR-0044; no API or delivery yet): `internal/webhooks` creates (receiving events from creation on), lists, reads, updates, rotates the signing secret of (the previous one keeps signing for 24 hours; one previous secret; an undecryptable one is replaced) and deletes a tenant's endpoints. `webhook:write` to change, `webhook:read` to see, tenant-wide only. URLs must be https without credentials or fragment, to an IP address or an ASCII DNS name (punycode), port 1–65535; they and the `whsec_` secrets are encrypted bound to tenant and endpoint, and reads and audit entries show only scheme, host and port. At most 10 endpoints per tenant, also under concurrent creates. Every change and refusal is audited.
- Webhook tables (ADR-0044): `webhook_endpoints` (URL and signing secrets encrypted), `webhook_cursors` (per-endpoint delivery position, lease and retry state) and `webhook_deliveries` (the delivery log), with row-level security and per-login column grants: the tenant pool manages endpoints and resets or moves cursors but never sees or writes the lease; the platform pool (the dispatcher) leases, records and disables but can't create or delete cursors. A cursor starts at or below its chain's last entry and only moves forward, to an existing entry or the chain's anchor, also when two updates race; cursors and records are same-tenant with their endpoint. CHECKs keep events to the catalog, delivery categories to fixed words (never an address) and success to 2xx.
- Docs: [Secret managers](docs/secret-managers.md) (ADR-0011 layers 1 and 2): what goes where (license key, license file, online lease, the server's own Secrets), with External Secrets Operator, Secrets Store CSI Driver, and Vault/OpenBao Agent (injector and VM) examples; Go SDK example `ExampleClient_Install_mounted` installs a mounted license file at start and on change.
- Go SDK lease stores (ADR-0004): `online.FileStore` (locked across processes, atomic, 0600; on `clock.FileStore`) and `online.KubernetesConfigMap` (one key of a ConfigMap, the ADR-0004 default; in-cluster API with the pod's service account, token re-read per request, conditional read-modify-write that keeps the rest of the object, conflicts retried with jitter, created if missing, names validated; RBAC example in the SDK README), with `online.KubernetesSecret` the same on a Secret (ADR-0004 amended). Standard library only.
- Logouts are audited (AU-2): `POST /auth/logout` records `user.logout` on the platform chain with the user, the session, source IP and user agent. The session ends first: if the entry can't be written, the answer is 500 (and the audit failure metric counts it), never a session kept alive. The NIST AU-2 entry now lists what is audited and every exception; AU-3 and AU-5 say how logins and logouts differ. A logout whose session can't be deleted keeps the cookie (500), so a retry can end it.
- `PlatformTenant.has_members` in the platform API (one query per page): whether anyone has joined the tenant. The platform Tenants screen offers "New owner invite" only for tenants without members, the only ones it works for (ADR-0042).
- Dashboard: "New owner invite" on each row of the platform Tenants screen (ADR-0042, amended): an owner email, then the new invite link shown once; a tenant that already has an owner says so. The create dialog and this one share the link view.
- Re-issue a tenant's owner invitation (ADR-0042, amended): `POST /api/v1/platform/tenants/{id|slug}/owner-invitation` with `{owner_email}` (platform admins) and `licenseforge tenant invite-owner --tenant SLUG|ID --owner-email E` (platform login), for a tenant whose first invitation was lost or expired. Only while the tenant has no owner (409 otherwise); earlier pending owner invitations are revoked; the new token is shown once. Audited on the platform chain (`tenant.owner_invitation`) and the tenant's (`invitation.revoke`, `invitation.create`).
- Dashboard: an "Offline" section on the license dialog for managers (ADR-0043): "Offline activation" (paste or upload a request; download `license.lic`, with its validity) and "Return a seat" (paste or upload a receipt). The request holds the license key: it stays in the component's state only and is cleared once answered; a retry after a network error or 5xx reuses the Idempotency-Key, a refusal gets a new one.
- CLI `licenseforge offline activate --request FILE > license.lic` and `licenseforge offline return --receipt FILE` (ADR-0043): carry an air-gapped machine's request or receipt to the API with an API token (`LICENSEFORGE_URL`, https only except loopback; `LICENSEFORGE_TENANT`, the slug; `LICENSEFORGE_TOKEN`); `-` reads stdin. Refusals print the API's code, detail and request ID and exit 1.
- Go SDK `offline` package (ADR-0043): `Request` (the `lfreq1` activation request for this machine), `Install` (verifies and stores the vendor's file; a renewal replaces it, an older file of the same license is refused with `ErrOlderFile` so a stale copy can't roll a renewal back), `Current` (re-reads and checks it on every use, so a file renewed by another process is picked up without a restart) and `Deactivate` (deletes the file, refuses it and older files of that license from then on, and returns the `lfrcpt1` receipt). State in any `clock.Store`, e.g. `clock.FileStore`; with a `clock.Guard` (on its own store), a file whose `iat` is ahead of the machine's clock is accepted within the guard's tolerance and raises the guard once installed. `clock.ErrLocked` (exported) and `clock.Guard.Tolerance` added.
- Offline seat return (ADR-0043): `POST /api/v1/tenants/{tenant}/deactivation-receipts` with `{"receipt": "lfrcpt1…"}` frees the machine's offline seat when the receipt names its current file, and answers the activation (200). A receipt for a seat already free (returned before, or deactivated from the dashboard) answers it unchanged with no new audit entry; another file of a seat still out (an older one: renewed since) answers `receipt_superseded` (409); no matching file of that machine, or a license outside the caller's scope, answers 404. Needs `activation:offline`; allowed whatever the license's status; audited as `activation.offline_return` with the receipt's hash (`activations.Service.Return`).
- Offline activation API (ADR-0043): `POST /api/v1/tenants/{tenant}/activation-requests` with `{"request": "lfreq1…"}` answers 201 with the signed `license_file`, `activation_id`, `kid`, `file_sha256` (what a deactivation receipt must carry) and `expires_at`. Needs `activation:offline` on the license's product (managers and up); `Idempotency-Key` replays the first answer after re-checking the caller's rights, the license (not revoked, suspended or expired since) and the seat (not returned since) (`activations.Service.OfflineTx`, `RecheckOffline`). New problem codes: `offline_not_allowed` (409), and `online_seat` (409). Each file of a machine is newer than the last, to the second (a request within that second waits for the next).
- Offline activation service (ADR-0043): `activations.Service.Offline` answers an `lfreq1` request carried in by a user or API token with `activation:offline` on the license's product. It takes or reuses the machine's seat under the online seat rules (ADR-0034) as an `offline` activation, and returns an `lf1` file bound to it, valid until the license's expiry capped at issue time + `max_offline_seconds` (grace only at the license's own expiry; no refresh). The activation records the file's `file_sha256` (new column `activations.offline_file_sha256`). Issues, renewals and refusals are audited as `activation.offline` with the request's hash, never the key or the request's content. Offline and online seats stay apart: the online API refuses an offline seat with `offline_seat` (409; Go SDK `online.ErrOfflineSeat`), and an offline request for a machine activated online is refused until it deactivates there (ADR-0043 amended).
- Offline activation formats (ADR-0043): the `lfreq1` activation request and the `lfrcpt1` deactivation receipt are specified (license format spec, "Offline activation") with conformance vectors in `spec/vectors/offline.json`; the Go SDK reads and writes them (`licensefile.ParseRequest`, `EncodeRequest`, `ParseReceipt`, `EncodeReceipt`, `FileSHA256`, `OfflineSHA256`). Nothing issues or accepts them yet.
- Audit entries from API actions record where they came from (AU-3): the client's address (the connection, or `X-Forwarded-For` from a trusted proxy) and user agent, and the request's `X-Request-Id` as `request_id` in the hashed details, so an entry leads to the request in the server logs. Before, only logins recorded the source. No schema or hash format change. ADR-0027 amended.
- Platform tenant onboarding API (ADR-0042). Until now, tenants could only be created in SQL.
  - `POST /api/v1/platform/tenants` with `{slug, name, owner_email}` creates a tenant **and an owner invitation** (every product, open 7 days) in one transaction on the platform pool. The invitation token is in the response only.
  - The platform admin doesn't join the tenant: the first owner signs in with the invited, verified email and accepts, like any invitation.
  - `GET /api/v1/platform/tenants` lists the tenants, newest first and cursor-paged, never the reserved platform tenant.
  - Callers must be platform admins with an enabled account, checked on every request. Other signed-in users get `403 forbidden`, and API tokens get 401 (tokens are tenant-scoped). CSRF is checked as on other session writes.
  - The admin role is rechecked inside the creating transaction under the admin-set lock, taken shared, so removing the admin or disabling the user waits for it.
  - A taken slug (including `platform`) is 409; invalid values are 422 with the field.
  - Audited: `tenant.create` on the platform chain, and `invitation.create` as the new tenant's first entry (never the email). Refusals go on the platform chain: invalid or taken values and role refusals on create (CLI refusals keep `via: cli`), and at the gate a non-admin's `session.platform_denied` or a weak session's `session.mfa_required`, once per session, with actor type `user` since the session wasn't admitted (partial index `auditevent_platform_denied`, built concurrently by migration `20261108155357_platform_denied_index.sql`). Platform MFA refusals count in `licenseforge_mfa_refusals_total`.
- `licenseforge tenant create --slug S --name N --owner-email E` (ADR-0042) does the same from the command line on the platform login (`LICENSEFORGE_PLATFORM_DATABASE_URL`). It's for installs without a platform admin yet, or without a browser, for example `kubectl exec deploy/licenseforge -- /licenseforge tenant create …`. The system is recorded as the actor (`via: cli`), and the invite path is printed once. New `store.OpenPlatform` opens the platform login alone, checked like the serving pools.
- Dashboard **Tenants** screen for platform admins (`/platform`, ADR-0042): every tenant, newest first, and a form that creates one and shows the first owner's invite link once (kept in the dialog only). `GET /auth/session` adds `platform_admin`, read on the identity login, so the nav link shows only for platform admins; it's a hint, and the platform API still checks on every request. A platform admin without tenants lands there. A session short of the platform MFA policy gets a step-up that comes back to it.
- `LICENSEFORGE_PLATFORM_MFA_POLICY` (ADR-0038): `none` (default), `mfa` or `phishing_resistant`. It applies to every platform request, and a session short of it gets `403 mfa_required` with a step-up that returns to `/platform/`. Platform admins are privileged accounts (IA-2(1)): the Secure Configuration Guide says to set it in production. An invalid value stops the server at start.
- Helm `extraCA.secretName` (and `extraCA.key`, `ca.crt` by default): a Secret with CA certificates the server trusts for outgoing TLS in addition to the image's bundle, e.g. an OIDC provider or a database (`sslmode=verify-full`) behind an internal or enterprise CA. Mounted read-only in the server, the migration Job and the audit-prune CronJob, and added through `SSL_CERT_DIR`; read at start. The e2e environment uses it instead of patching the Deployment.

### Fixed
- Customer archive is one-way and at the database clock, as for products, features and plans: a restrictive UPDATE policy (`archive_once` on `customers`) refuses un-archiving or re-dating an archived customer from the serving logins, including an update or upsert racing a concurrent archive; renaming an archived customer still works. Migration `20261107090000_snapshot_match_security.sql`.
- Policies that compare a row with its previous version (`use_moves_forward` on `api_tokens`, `forward_to_entry` on `audit_export_cursors`) now also match that version in USING. Before, an UPDATE that waited for a concurrent commit was rechecked against the newer row while the policy's subquery still read the older snapshot, so it could move `last_used_at` or an export cursor back past what had just been committed. Such an update now changes nothing and an upsert is refused. Token revoke and member removal (locking the member's tokens) look again, in new statements, until a plain read shows no active token left out (at most five times, then an error rather than a removal that keeps a token active); customer changes look again once when a lock waited for a concurrent archive. `TestLagAndFailureMetrics` no longer depends on timing.

- `internal/secrets` (ADR-0025): keyring of master keys from `LICENSEFORGE_MASTER_KEYS` (generate one with `openssl rand -base64 32`), AES-256-GCM encryption bound to its row, HMAC lookup hashes that survive key rotation.
- `internal/licensekey`: license keys `LF-` + 128 random bits in grouped base32, normalised input with one canonical spelling.
- `internal/authz` (ADR-0019): built-in roles owner/admin/manager/support/viewer and the token-only sdk role, mapped to fixed permissions; `Require` per handler, explicit product scope (zero scope denies), `Products` for list filters, `CanAssign` for member and token changes; scoped principals can't manage access; only owners grant, change or remove owner; tenant settings are owner-only.
- `internal/apitoken`: API tokens `lf_live_` + 256 random bits + CRC-32 checksum (secret-scanner friendly), offline format check, SHA-256 lookup hash and a display prefix.
- Audit log: one hash-chained, append-only chain per tenant, written in the action's transaction and serialized per tenant; `Verify` detects changed, removed or reordered entries (ADR-0027).
- Per-tenant Ed25519 signing keys with a pending → active → retired lifecycle; private keys encrypted with the master keyring and erased from the live table on retirement; `Signer` interface with a local implementation (ADR-0026).
- License invariants: term licenses always have an expiry, site licenses start at issue with no activation limit, limits are fraction-free integers with key-format names.
- Customers, licenses and activations tables (ADR-0013): plan snapshot (incl. binding policy) and resolved entitlements checked like the license format, encrypted key with per-tenant lookup hash, status and expiry invariants (expiry derived), activations bound as the license requires, one active activation per machine, never deleted, same-tenant keys and forced RLS; plans gain a binding policy.
- Catalog tables (ADR-0015): features, plans (calendar-month or second terms) and plan features; keys, slugs and types immutable and rows archived, never deleted, enforced by column-level grants; database-enforced formats and ranges; same-tenant/same-product/type composite keys; schema-vs-migration and same-tenant structural guard tests.
- Go SDK module `licenseforge.io/licenseforge/sdk/go` with `licensefile`: sign and verify `lf1` licenses (Ed25519, key ID in the envelope, algorithm bound to the trusted key).
- `lf1` conformance vectors in `spec/vectors/lf1.json`.
- `internal/issue`: signed offline license files for site licenses (air-gapped installs): `activation:offline` on the product, active and unexpired license with offline allowed, the tenant's active key, expiry rounded down, and an audit entry (`license.offline_file`) written before the file is returned; denied and failed attempts are audited too. The server module now uses the Go SDK module (`replace => ./sdk/go`, ADR-0023).
- `licensefile.Encode`: writes the lf1 payload for issuers and refuses claims that `ParseClaims` wouldn't read back identically (no rounding, no silently dropped fields).
- `licensefile.ParseClaims`, `Claims.Check` and `Open`: parse and check lf1 claims (version, product, binding, clock skew, not-before, max offline, expiry with grace, updates_until) in the order defined by the spec.
- Claim conformance vectors in `spec/vectors/lf1-claims.json` (98 cases); fingerprint derivation vectors in `spec/vectors/fingerprint.json`.
- `Entitlements.HasFeature`, `Limit` and `Allows` (ADR-0015): unknown keys are never an error; an absent limit behaves as 0; `Allows` takes the resulting total and rejects negative values.
- Go SDK `clock` package: clock rollback protection (ADR-0018): HMAC-authenticated high-water mark, `Now`/`Observe`/`Reset`, 24h default tolerance (0 = strict), rollback check that always runs (also on read-only storage), and a `FileStore` with OS file locks that is atomic and safe across processes.
- CI runs the SDK's OS-specific tests on Windows only; macOS returns with a self-hosted runner (darwin is still type-checked by `make vet-cross`).
- CI runs tests in FIPS 140-3 mode (`GOFIPS140=certified`).
- Go SDK `fingerprint` package: default machine/cluster fingerprints (vendor override, opt-in `LICENSEFORGE_FINGERPRINT`, Kubernetes kube-system UID with retries, Linux machine-id with tmpfs and container safeguards, Windows MachineGuid, macOS IOPlatformUUID), hashed per tenant and product.
