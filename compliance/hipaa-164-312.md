# HIPAA Security Rule: technical safeguards (45 CFR §164.312)

LicenseForge is **PHI-free by design** (ADR-0024). No field needs health data, and the [data inventory](data-inventory.md) lists everything it stores. Don't put PHI in names, emails, `external_refs` or audit details. This mapping is for covered entities and business associates that run LicenseForge inside an environment that handles ePHI. It shows what the product provides for each safeguard; the safeguard itself is met by the whole system. LicenseForge isn't "HIPAA certified" (no such certification exists). A BAA comes only with the future hosted offering.

R = required, A = addressable. Status uses the terms of the [control matrix](nist-800-53-matrix.md).

| Safeguard | | Status | What LicenseForge provides | Operator's part | 800-53 |
|---|---|---|---|---|---|
| **(a)(1) Access control** | R | partial | Tenant-scoped roles checked in Go (`authz.Require`) in the API token and offline-issuance services, with forced row-level security behind them, and five database logins with separate rights (only the tenant login is tenant-scoped; only the retention login may delete audit entries) | Assign roles per least privilege; review members. Signing key and platform operations have no authorization check yet | AC-3, AC-6 |
| (a)(2)(i) Unique user identification | R | implemented | Each person is one user, keyed by the IdP's `(issuer, subject)`, never by a shared email. API tokens are per integration, each with its own ID and creator | One IdP account per person; no shared accounts | IA-2, IA-4 |
| (a)(2)(ii) Emergency access procedure | R | inherited | The platform pool and the owner database login can reach every tenant's data. Platform admins (the last one can't be removed) will act across tenants with audit; the `LICENSEFORGE_BOOTSTRAP_ADMIN` setting isn't wired into the server yet | Write and test a break-glass procedure: who may use the owner login and how it is logged | AC-2 |
| (a)(2)(iii) Automatic logoff | A | implemented | Sessions end after a configurable idle timeout (default 1 hour) and max age (default 12 hours), server-side by the database clock; logout ends the session | – | AC-12, AC-12(1) |
| (a)(2)(iv) Encryption and decryption | A | partial | Secrets only: license keys and signing keys are encrypted with AES-256-GCM under the master keyring; tokens and session secrets are stored only as hashes. Other data isn't encrypted by the application | Encrypt database disks and backups (covers all other data); keep the master keys in a secret manager | SC-28, SC-28(1) |
| **(b) Audit controls** | R | partial | A hash-chained, append-only audit log per tenant, written in the action's transaction. Today it records API token changes and offline license issuance, including denied attempts | Login events, SIEM export and retention are planned (Roadmap v0.1); until then, collect the server's JSON logs | AU-2, AU-3, AU-9, AU-12 |
| **(c)(1) Integrity** | R | implemented | Serving logins can't delete licenses, customers or activations, and can't change or delete audit entries. Database constraints enforce license invariants; license files are signed with Ed25519 | Restrict the owner login | SI-7, AU-9 |
| (c)(2) Mechanism to authenticate ePHI | A | implemented | Licenses are verified by signature. The audit chain's `Verify` detects changed, reordered or removed entries. Encrypted values are authenticated (GCM) and bound to their row | Export the audit chain head to detect truncation | SC-13, AU-9 |
| **(d) Person or entity authentication** | R | partial | OIDC login with PKCE, state and nonce, and a fully verified ID token; API tokens are 256-bit, hashed and expiring. MFA is whatever the IdP enforces | Enforce MFA in the IdP. Sessions record the IdP's assurance (`amr`/`acr`) and tenants can set an MFA policy; per-request enforcement follows (ADR-0038) | IA-2, IA-2(1), IA-5 |
| **(e)(1) Transmission security** | R | partial | OIDC URLs must be https; cookies are `Secure` with the `__Host-` prefix | Terminate TLS 1.2+ at the ingress; connect to PostgreSQL with `sslmode=verify-full` (the server doesn't enforce database TLS; the driver default `prefer` can fall back to plaintext) | SC-8 |
| (e)(2)(i) Integrity controls | A | partial | Same as (e)(1); signed license files carry their own integrity | Same as (e)(1) | SC-8 |
| (e)(2)(ii) Encryption | A | partial | Same as (e)(1). The server itself listens on plain HTTP inside the pod network | TLS at the ingress, or a service mesh with mTLS to the pod | SC-8 |
